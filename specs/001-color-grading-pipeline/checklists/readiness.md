## Requirement Completeness

- [x] CHK002 - Is there a requirement for a client to query which parts have already been received for a given upload — needed to actually resume per FR-030 — or is resume assumed to rely solely on client-side state that may itself be lost? - [x] CHK003 - Is a maximum (or expected) source file size / duration bound documented anywhere the system is required to handle? [Gap, Plan §Scale/Scope]

- [ ] CHK008 - Is the acceptable deviation around "within the validated ~1.08x-realtime benchmark" in SC-003 bounded (e.g., a percentage tolerance), or is "within" left open to interpretation? [Ambiguity, Spec §SC-003]

- [ ] CHK011 - Does FR-027's "(e.g., via a checkbox)" risk prescribing a UI implementation detail inside a functional requirement, rather than describing the underlying capability itself? [Clarity, Spec §FR-027]

## Requirement Consistency

- [ ] CHK012 - Does FR-019's "bounded period after creation" match the TTL-refreshed-on-every-write behavior described in the plan/research, or do the two describe different expiry semantics (from creation vs. from last update)? [Conflict, Spec §FR-019]
- [ ] CHK013 - Does FR-032's "MUST let a client (or the system) abort" a stalled upload sit consistently alongside the out-of-scope declaration for "S3 object lifecycle management," or could the parenthetical be read as requiring automatic background cleanup that scope explicitly excludes? [Conflict, Spec §FR-032]
- [ ] CHK014 - Is the contract's job-submission error-handling note (sync rejection vs. async `failed` outcome for an unavailable *explicit* profile) consistent with how FR-013 itself is worded, or does the spec leave that timing choice open in a way the contract has had to guess at? [Consistency, Spec §FR-013]
- [ ] CHK015 - Is the "GPU worker concurrency default of 1 (max 2)" (FR-018) scoped explicitly to a single worker process, or could two independently-configured worker processes on the same GPU host each apply the cap and jointly exceed it? [Gap, Spec §FR-018]

- [ ] CHK017 - Can SC-010's "no perceptible quality loss" be objectively verified, or does it rely on an undefined perceptual test/threshold? [Measurability, Spec §SC-010]

## Scenario Coverage

- [ ] CHK020 - Are requirements defined for submitting a job against an `s3_key` that already has another job in flight (duplicate/concurrent submission for the same source)? [Coverage, Gap]
- [x] CHK021 - Are requirements defined for what a client should do if it loses its own upload-progress state entirely (e.g., browser closed mid-upload) and must discover already-received parts from scratch? [Coverage, Gap, Spec §FR-030] — **Resolved**: same fix as CHK002 (FR-034), plus the matching edge case in spec.md.
- [ ] CHK022 - Are recovery requirements defined for a worker that crashes mid-job beyond "eventually expires via TTL" — e.g., a bounded time-to-detection rather than a potentially multi-hour wait? [Coverage, Gap, Spec Edge Cases]
- [ ] CHK023 - Are requirements defined for a client to distinguish "`auto` resolved to GPU" from "I explicitly requested GPU and got it," or is `resolved_profile` alone assumed sufficient without stating so? [Coverage, Spec §FR-012, data-model.md]

## Edge Case Coverage

- [ ] CHK024 - Are the "abandoned multipart upload" and "job referencing an incomplete upload" edge cases distinguished clearly enough to know they map to two different failure points (upload-time vs. job-submission-time), or could they be read as the same case? [Clarity, Spec Edge Cases]
- [ ] CHK025 - Is there a defined precedence when `max_quality: true` is submitted together with `profile: "d-log-m"` (a stub profile) — which rejection reason takes priority? [Coverage, Gap, Spec §FR-015, §FR-027]
- [ ] CHK026 - Are edge cases addressed for storage becoming unreachable mid-job (source download or result upload failing at the storage layer, distinct from an `ffmpeg`-level failure)? [Coverage, Gap]

## Non-Functional Requirements

- [ ] CHK028 - Are requirements defined for how unguessable/secure presigned download URLs need to be, given no authentication sits in front of them (FR-001, FR-006)? [Gap, Assumption]

- [ ] CHK030 - Are requirements defined for an `hlg-gpu` job that is already `running` when the GPU becomes unavailable mid-job (e.g., driver fault), distinct from the "GPU unavailable at submission time" case already covered by FR-013? [Coverage, Gap]
